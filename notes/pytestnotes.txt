============================================================
FASTAPI TESTING — COMPLETE NOTES
============================================================


1. WHAT IS TESTING?
============================================================

Testing means checking whether our application behaves
as expected.

Instead of manually checking every API through Swagger,
we write automated tests.

Manual:

Swagger
   ↓
Send request
   ↓
Check response manually


Automated:

pytest
   ↓
Send request
   ↓
Check expected result
   ↓
PASS ✅ / FAIL ❌


Simple definition:

TESTING = Automatically checking that our code/API behaves
as expected.


============================================================
2. WHY DO WE NEED TESTING?
============================================================

Testing helps us find:

- Bugs
- Incorrect responses
- Invalid input handling problems
- Database problems
- Broken API logic
- Unexpected behavior after code changes


Example:

We change:

GET /employees


A test can automatically check:

- Status code
- Response data
- Error handling
- Filtering
- Searching
- Pagination


Instead of manually checking everything again.


============================================================
3. PYTEST
============================================================

pytest is a Python testing framework.


Install:

Run tests:

Run with more information:

10. WHY IMPORT app?
============================================================

Our routes should NOT necessarily be inside main.py.


Example structure:

main.py
   ↓
FastAPI app
   ↓
include_router()
   ↓
api/routes/employee.py


main.py:

from fastapi import FastAPI

from api.routes.employee import router as employee_router


app = FastAPI()

app.include_router(employee_router)


Routes remain inside:

api/routes/employee.py


Testing imports the application:

from main import app


Why?

Because:

TestClient(app)


needs to know:

"Which FastAPI application should I send the request to?"


TestClient does NOT require routes to be written inside
main.py.

Employee created


But if using real DB:

Employee is actually inserted.


Repeated tests can create:

John
Mike
David
John2
John3
...


A test database keeps testing isolated.

34. PYTEST FIXTURES
============================================================

A fixture provides reusable setup for tests.


Example:

import pytest


@pytest.fixture
def employee():

    return {
        "name": "John",
        "email": "john@gmail.com"
    }


Now use it:

def test_employee(employee):

    assert employee["name"] == "John"


Instead of recreating the same data in every test.


============================================================
35. WHY FIXTURES?
============================================================

Without fixture:

def test_one():

    employee = {
        "name": "John",
        "email": "john@gmail.com"
    }


def test_two():

    employee = {
        "name": "John",
        "email": "john@gmail.com"
    }


Repeated code.


With fixture:

@pytest.fixture
def employee():

    return {
        "name": "John",
        "email": "john@gmail.com"
    }


Then:

def test_one(employee):

    ...


def test_two(employee):

    ...


Cleaner and reusable.

============================================================
46. COMMON TESTING MISTAKES
============================================================

MISTAKE 1:

Testing only successful requests.


Always test error cases too.


MISTAKE 2:

Testing against the real production database.


Use a test database.


MISTAKE 3:

Depending on test execution order.


Tests should be independent.


MISTAKE 4:

Checking only status code.


Also check response data when appropriate.


MISTAKE 5:

Putting all test setup repeatedly in every test.


Use fixtures.


MISTAKE 6:

Putting application routes inside test files.


Tests should call the actual application.


MISTAKE 7:

Confusing TestClient with a real browser/client.


TestClient is used to programmatically test the FastAPI
application.
