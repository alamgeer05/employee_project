PATH PARAMETER AND QUERY PARAMETER
==================================

Path parameter
--------------

A path parameter is part of the URL path. Use it when identifying one
specific resource.

    from fastapi import APIRouter

    router = APIRouter()

    @router.get("/employees/{employee_id}")
    def get_employee(employee_id: int):
        return {
            "message": "Employee found",
            "employee_id": employee_id
        }

Call it like this:

    GET /employees/5

Here, 5 is the path parameter.

    /employees/{employee_id}
               ^^^^^^^^^^^^
               path parameter

Use path parameters when the value is required to identify something:

    /employees/5
    /users/10
    /products/25

Query parameter
---------------

A query parameter comes after ? in the URL. Use it for filtering, searching,
sorting, pagination, or optional settings.

    @router.get("/employees")
    def get_employees(
        department: str | None = None,
        page: int = 1
    ):
        return {
            "department": department,
            "page": page
        }

Call it like this:

    GET /employees?department=IT&page=2

Here, department=IT and page=2 are query parameters.

    /employees?department=IT&page=2
              ^^^^^^^^^^^^^^^^^^^^^
              query parameters

Main difference
---------------

    Path parameter:  /employees/5
    Query parameter: /employees?department=IT

    Path parameter  -> identifies the resource
    Query parameter -> filters or modifies the request

Both together
-------------

    @router.get("/employees/{employee_id}")
    def get_employee(
        employee_id: int,
        include_salary: bool = False
    ):
        return {
            "employee_id": employee_id,
            "include_salary": include_salary
        }

Call it like this:

    GET /employees/5?include_salary=true

    5                   -> path parameter
    include_salary=true -> query parameter

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

DATABASE_URL = "sqlite:///./task_manager.db"

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False}
)

SessionLocal = sessionmaker(
    autocommit=False,
    autoflush=False,
    bind=engine
)

Base = declarative_base()


def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()


Engine = connection/configuration between Python and database.
Session = our conversation with the database.

When we want to:

INSERT
SELECT
UPDATE
DELETE

we use a database session.




3. Base
Base = declarative_base()

This is the base class from which we'll create our database models.

class Task(Base):

SQLAlchemy then understands:

"Task is a database model."


changes for postgres and sqlite

connect_args={"check_same_thread": False}

This is commonly used with SQLite in FastAPI because of SQLite's thread behavior.











Why yield?

Think of it like:

Request comes
     ↓
create DB session
     ↓
give session to route
     ↓
route uses DB
     ↓
request finishes
     ↓
close DB session

So:

def get_db():
    db = SessionLocal()      # open session
    try:
        yield db             # give it to FastAPI/route
    finally:
        db.close()           # close it

Then later in a route:

from fastapi import Depends
from sqlalchemy.orm import Session

@router.get("/tasks")
def get_tasks(db: Session = Depends(get_db)):
    ...

FastAPI sees:

Depends(get_db)

and automatically calls get_db() for that request.

--------------------------------------FastAPI/API Fundamentals — Part 1--------------------------

Think of every API request like this:

CLIENT
  │
  │  Request
  │  ──────────────────>
  │
  │       FastAPI
  │
  │  <──────────────────
  │  Response

A request mainly has:

METHOD + PATH + QUERY + BODY

And response mainly has:

STATUS CODE + RESPONSE BODY









1. Path

Definition: The URL endpoint that identifies what resource/API you are accessing.

Example:

@app.get("/tasks")
def get_tasks():
    return {"message": "All tasks"}

Request:

GET /tasks
Why use?

To identify the API/resource.

/users
/tasks
/products





2. HTTP Methods

They tell the server what you want to do.

Method	Meaning	Example
GET	Get data	Get tasks
POST	Create data	Create task
PUT	Replace/update entire data	Replace task
PATCH	Update part of data	Change task status
DELETE	Delete data	Delete task

Simple memory:

GET     → Give me
POST    → Create
PUT     → Replace
PATCH   → Change
DELETE  → Remove







3. Path Parameter

Used when you want a specific resource.

@app.get("/tasks/{task_id}")
def get_task(task_id: int):
    return {"task_id": task_id}

Request:

GET /tasks/10

FastAPI gives:

task_id = 10

Response:

{
    "task_id": 10
}







4. Query Parameter

Used mainly for filtering, searching, sorting, pagination, etc.

@app.get("/tasks")
def get_tasks(status: str):
    return {"status": status}

Request:

GET /tasks?status=completed

FastAPI gets:

status = "completed"

Response:

{
    "status": "completed"
}
Difference
/tasks/10
       ↑
Path parameter
→ specific task


/tasks?status=completed
       ↑
Query parameter
→ filter/search





5. Request Body

Used when the client needs to send data to the server.

Most commonly with POST, PUT, PATCH.

Example:

@app.post("/tasks")
def create_task(task: dict):
    return task

Client sends:

{
    "title": "Learn FastAPI",
    "status": "pending"
}

That's the request body.

Think:

Request body = Data sent TO the API







6. Schema

Instead of accepting any random dictionary, we define what data we expect.

from pydantic import BaseModel

class TaskCreate(BaseModel):
    title: str
    status: str

Then:

@app.post("/tasks")
def create_task(task: TaskCreate):
    return task

Client:

{
    "title": "Learn FastAPI",
    "status": "pending"
}

FastAPI/Pydantic checks:

title → must be string
status → must be string

So:

Schema = Structure/rules for incoming or outgoing data.





7. Response

The data API sends back to the client.

@app.get("/hello")
def hello():
    return {"message": "Hello"}

Response:

{
    "message": "Hello"
}

Think:

Request body  → Client → Server
Response      → Server → Client





8. Response Model

We can also define what our API is allowed to return.

class TaskResponse(BaseModel):
    id: int
    title: str
    status: str

Then:

@app.get("/tasks/{task_id}", response_model=TaskResponse)
def get_task(task_id: int):
    return {
        "id": task_id,
        "title": "Learn FastAPI",
        "status": "pending"
    }
Why?

To keep the response structure controlled.

Especially useful when your database model contains things you don't want to expose.









| Code  | Meaning      | Common use                   |
| ----- | ------------ | ---------------------------- |
| `200` | OK           | Successful GET               |
| `201` | Created      | Successful POST              |
| `204` | No Content   | Successful DELETE            |
| `400` | Bad Request  | Invalid request              |
| `401` | Unauthorized | Login/token required         |
| `403` | Forbidden    | User doesn't have permission |
| `404` | Not Found    | Task/user doesn't exist      |
| `500` | Server Error | Unexpected backend error     |



2xx → Success
4xx → Client/request problem
5xx → Server problem

1. What is Pydantic?

Pydantic validates and structures the data coming into or going out of your FastAPI API.

















from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int

If request is:

{
  "name": "Alam",
  "age": 24
}

✅ Valid.

If:

{
  "name": "Alam",
  "age": "hello"
}

❌ Validation error because age should be an integer.

2. BaseModel

Every normal Pydantic schema inherits from:

BaseModel

Example:

class UserCreate(BaseModel):
    name: str
    age: int

Think:

BaseModel = tells Pydantic "this class is a data schema."

3. Request Schema

Used to define what client is allowed/expected to send.

class UserCreate(BaseModel):
    name: str
    email: str
    age: int

Request:

{
  "name": "Alam",
  "email": "alam@gmail.com",
  "age": 24
}

This is:

Client
  ↓
JSON
  ↓
UserCreate
  ↓
Validation
  ↓
Your API logic
4. Response Schema

Used to define what API should return.

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

Then:

@app.get("/users/{id}", response_model=UserResponse)
def get_user(id: int):
    ...

Now FastAPI expects the response to follow:

{
  "id": 1,
  "name": "Alam",
  "email": "alam@gmail.com"
}
5. Why Create and Response Schemas Separately?

Very important.

Suppose user creates an account.

Client sends:

{
  "name": "Alam",
  "email": "alam@gmail.com",
  "password": "secret123"
}

So:

class UserCreate(BaseModel):
    name: str
    email: str
    password: str

But you shouldn't return the password.

So:

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

Therefore:

UserCreate
→ What client SENDS

UserResponse
→ What API RETURNS

This is one of the most important concepts.

6. Field Validation

You can put rules on fields.

Example:

from pydantic import BaseModel, Field

class UserCreate(BaseModel):
    name: str = Field(min_length=3)
    age: int = Field(ge=18)

Meaning:

name → minimum 3 characters
age  → greater than or equal to 18

So:

{
  "name": "Al",
  "age": 16
}

❌ Validation fails.

7. Default Value

You can provide a default.

class TaskCreate(BaseModel):
    title: str
    status: str = "pending"

Client can send:

{
  "title": "Learn FastAPI"
}

Pydantic automatically uses:

status = "pending"
8. Optional Field

Suppose phone number isn't required.

from typing import Optional

class UserCreate(BaseModel):
    name: str
    phone: Optional[str] = None

Client can send:

{
  "name": "Alam"
}

✅ Valid.

Because:

phone = None
9. Update Schema

This is where partial update becomes important.

Create:

class UserCreate(BaseModel):
    name: str
    email: str
    age: int

For update, maybe user only wants to change their name:

{
  "name": "Alam Khan"
}

So we create an update schema where fields can be optional:

class UserUpdate(BaseModel):
    name: str | None = None
    email: str | None = None
    age: int | None = None

Now user can send only:

{
  "name": "Alam Khan"
}

This is commonly used with:

PATCH

Sometimes JSON contains objects inside objects.

Example:

{
  "name": "Alam",
  "address": {
    "city": "Noida",
    "pincode": 201301
  }

Schemas:

    city: str

Very important distinction.

SQLAlchemy Model

Defines your database table.

class User(Base):
    id
    name
    email
    password
Pydantic Schema

Defines your API data.

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

Think:

SQLAlchemy Model
        ↓
DATABASE

Pydantic Schema
        ↓
API
12. ORM → JSON

Database gives you a SQLAlchemy object:

User object
    ↓
id = 1
name = Alam
email = alam@gmail.com

But API should return JSON:

{
  "id": 1,
  "name": "Alam",
  "email": "alam@gmail.com"
}

Pydantic/FastAPI helps convert/serialize the data into the response format.

In modern Pydantic, when returning ORM objects, you'll commonly configure the response schema with:

from pydantic import BaseModel, ConfigDict

class UserResponse(BaseModel):
    id: int
    name: str
    email: str

    model_config = ConfigDict(from_attributes=True)

from_attributes=True basically says:

"I can build this schema from an object whose attributes are id, name, email, etc."







1. Enum — restrict allowed values

Suppose our Task has a status:

pending
completed
cancelled

We don't want someone sending:

{
  "title": "Learn FastAPI",
  "status": "abcd"
}

So we use Enum.

from enum import Enum
from pydantic import BaseModel

class TaskStatus(str, Enum):
    pending = "pending"
    completed = "completed"
    cancelled = "cancelled"


class TaskCreate(BaseModel):
    title: str
    status: TaskStatus

Now:

{
  "title": "Learn FastAPI",
  "status": "completed"
}

✅ Valid.

But:

{
  "title": "Learn FastAPI",
  "status": "abcd"
}

❌ Invalid → Pydantic validation error.

Why use Enum?

Without Enum:

status: str

means any string is allowed.

With Enum:

status: TaskStatus

means only predefined values are allowed.

Think:

str
 ↓
"anything"

Enum
 ↓
"pending" | "completed" | "cancelled"

That's basically it.

2. ORM → Pydantic Schema

This one is about database object → API response.

Suppose SQLAlchemy gives us a database object:

task = Task(
    id=1,
    title="Learn FastAPI",
    status="completed"
)

This is a Python/SQLAlchemy object, not JSON.

But our API needs to return:

{
  "id": 1,
  "title": "Learn FastAPI",
  "status": "completed"
}

So we create a Pydantic response schema:

from pydantic import BaseModel, ConfigDict

class TaskResponse(BaseModel):
    id: int
    title: str
    status: str

    model_config = ConfigDict(from_attributes=True)

The important part:

model_config = ConfigDict(from_attributes=True)

means:

"Pydantic, you can read values from the attributes of a Python/ORM object."

So:

SQLAlchemy object
        ↓
   TaskResponse
        ↓
      JSON
        ↓
     Client
Without from_attributes=True

Pydantic mainly expects dictionary-like input:

{
    "id": 1,
    "title": "Learn FastAPI",
    "status": "completed"
}
With from_attributes=True

It can work with:

task.id
task.title
task.status

which is exactly how a SQLAlchemy model behaves.

The important distinction

Don't mix these two:

SQLAlchemy Model
        ↓
represents DATABASE TABLE

Pydantic Schema
        ↓
represents API DATA

Example:

# SQLAlchemy
class Task(Base):
    id
    title
    status

↓

# Pydantic
class TaskResponse(BaseModel):
    id: int
    title: str
    status: str

    model_config = ConfigDict(from_attributes=True)

↓

{
  "id": 1,
  "title": "Learn FastAPI",
  "status": "completed"
}
🧠 Just remember

Enum:

"Which values are allowed?"

from_attributes=True:

"Take data from my SQLAlchemy object's attributes and fit it into my Pydantic schema."

That's all you need to understand for now.

11. Depends() — Dependency Injection

Forget database for one minute.

Suppose many routes need the same function:

def common_function():
    return "Hello"

Instead of manually calling it:

@app.get("/tasks")
def tasks():
    data = common_function()
    ...

FastAPI lets us say:

from fastapi import Depends

@app.get("/tasks")
def tasks(data = Depends(common_function)):
    return data
What does this mean?
Depends(common_function)

means:

"FastAPI, call common_function() for me and give its result to this parameter."

12. Why is this called Dependency Injection?

Simple:

Route needs something
       ↓
Dependency provides it
       ↓
FastAPI injects it

Example:

Route needs → current user
Dependency → get_current_user()

or:

Route needs → database session
Dependency → get_db()

or:

Route needs → settings
Dependency → get_settings()
13. Now get_db() makes sense

We already created:

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

Now in a route:

from fastapi import Depends
from sqlalchemy.orm import Session

@router.get("/")
def get_tasks(db: Session = Depends(get_db)):
    return {"message": "Using database"}

The flow is:

GET /tasks
     ↓
FastAPI
     ↓
Depends(get_db)
     ↓
get_db()
     ↓
create DB session
     ↓
give session to `db`
     ↓
route uses `db`
     ↓
request finishes
     ↓
db.close()
Why yield here?

Because we want:

BEFORE route
→ create DB session

AFTER route
→ close DB session

yield lets the dependency provide the value and then continue cleanup afterward.

Task ko kaise pata chalega ki woh kis user ka hai?

33. What is ForeignKey?

Simple definition:

ForeignKey connects one table's column to another table's primary key.

For example:

user_id = Column(Integer, ForeignKey("users.id"))

Meaning:

tasks.user_id refers to users.id.

So:

users
----------------
id
1
2
3

        ↑
        │
        │ ForeignKey
        │
        ↓

tasks
----------------
id    title             user_id
1     Learn FastAPI        1
2     Learn SQLAlchemy     1
3     Learn Docker         2

Task 1 and Task 2 belong to User 1.

Task 3 belongs to User 2.

34. Why not just store user_id?

You might ask:

"Bro, why do we need ForeignKey? Can't I just do user_id = Column(Integer)?"

Technically, you can store an integer.

But then the database doesn't know that:

tasks.user_id

is supposed to refer to:

users.id

With ForeignKey, we explicitly establish that relationship.

users.id
     ↑
     │
ForeignKey
     │
     ↓
tasks.user_id

37. What is relationship()?

ForeignKey establishes the database connection.

But SQLAlchemy also gives us:

relationship()

which makes it easier to work with the related Python objects.

Example:

User
from sqlalchemy.orm import relationship

class User(Base):
    __tablename__ = "users"

    id = Column(Integer, primary_key=True)
    name = Column(String)

    tasks = relationship("Task", back_populates="user")
Task
class Task(Base):
    __tablename__ = "tasks"

    id = Column(Integer, primary_key=True)
    title = Column(String)

    user_id = Column(Integer, ForeignKey("users.id"))

    user = relationship("User", back_populates="tasks")

Now SQLAlchemy understands:

User
  │
  │ tasks
  ↓
[Task, Task, Task]

and:

Task
  │
  │ user
  ↓
User
38. back_populates

This:

tasks = relationship("Task", back_populates="user")

and this:

user = relationship("User", back_populates="tasks")

tell SQLAlchemy:

These two relationships are connected to each other.

So:

User.tasks
     ↕
Task.user
39. One-to-Many Relationship

Our example is:

One User → Many Tasks

That's called a one-to-many relationship.

One User
   │
   ├── Task 1
   ├── Task 2
   └── Task 3

In SQLAlchemy:

User.tasks

returns multiple tasks.

While:

Task.user

returns one user.

40. Very important: ForeignKey vs relationship

Don't confuse them.

ForeignKey
user_id = Column(Integer, ForeignKey("users.id"))

Responsible for:

Database-level connection

relationship()
tasks = relationship("Task")

Responsible for:

Python/SQLAlchemy-level convenient access

Mental model:

ForeignKey
    ↓
Database connection

relationship()
    ↓
Python object connection
